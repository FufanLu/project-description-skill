## 2 核心模型：短链的生命周期

<a id="s2-1"></a>

### 2.1 先说什么是状态机

拿网购订单举例：待支付 → 已支付 → 已发货 → 已完成。订单在「已发货」时再点「修改地址」，系统直接拒绝，因为规则表里没有这一条。短链也一样：「过期」的短链不能跳转，只能续期或归档。

![图 2 · 短链的生命周期](../img/demo_state.png)

<i>图 2 · 短链的生命周期。上面的弧线是前进，下面的虚线是退回。</i>

### 2.2 真实代码

```python
def apply(link, cmd, actor):                      # 纯函数：只判断，不读写存储
    if cmd.expected_version != link.version:      # 基于旧版本的命令直接拒
        raise VersionConflict(link.version)
    rule = RULES.get((link.status, cmd.name))     # 规则表里没有这一条 → 拒绝
    if rule is None or actor not in rule.actors:
        raise InvalidTransition(link.status, cmd.name)
    return link.evolve(status=rule.to, version=link.version + 1)
```

## 3 链路一：一次跳转

![图 3 · 一次跳转](../img/demo_seq.png)

<i>图 3 · 一次跳转。圆圈里的编号和下面的步骤一一对应。</i>

1. 浏览器请求 `GET /abc123`。入口先查短码格式 【确定性】，不合法直接 404。
2. 查 Redis。命中就直接进第 7 步。
3. 没命中：查 MySQL，再回填缓存（第 4–6 步）。
4. 状态闸门 【护栏】：不是 ACTIVE 或已过期，返回 410。

> <b>为什么先查缓存（W2）</b>
>
> 跳转是读多写少。先查 Redis，大部分请求不碰数据库。缓存设 600 s 过期兜底。

## 4 为什么这样设计：2 个追问

<a id="w1"></a>

#### W1 为什么分成接入、服务、存储三层？

接入层只做校验和鉴权，业务逻辑放服务层，存储只经过 repo 接口。这样换存储时业务代码不用改。代价是多一层接口，简单查询也要写一个 repo 方法。

<sub>出处：service/README.md（虚构）</sub>

<a id="w2"></a>

#### W2 为什么先查缓存，而不是直接查库？

跳转是读多写少。先查 Redis，没命中再查库并回填，大部分请求不碰数据库。代价是改目标地址后要删缓存；删失败时最多读到 600 s 的旧值，所以缓存一定设过期时间。（最后半句是我的理解。）

<sub>出处：service/redirect.py 的注释（虚构）</sub>
