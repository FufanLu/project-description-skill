# 讲义结构与写法

读者是准备面试的用户本人。面试官会顺着讲义里的每一句往下追问。讲义要让用户做到四件事：

1. 一分钟讲清项目是什么、解决什么。
2. 画得出系统结构图。
3. 讲得清每条关键链路，包括失败了怎么办。
4. 答得出每个「为什么这样设计」，而且能落到代码。

## 章节顺序

| 章 | 内容 |
|---|---|
| 标题区 | `# {项目名} · {一句话定位}讲义`；一段导语；一行斜体元信息（对照哪个仓库 · 面向什么岗位 · 年月） |
| 目录 | `## 目录` 块，格式见 output-and-checks.md |
| 0 怎么读 | 一句话讲清讲义讲什么；标签说明；W 编号说明；阅读顺序 |
| 1 项目介绍 | 是什么 · 要解决的问题 · 核心思路 · 系统全貌 · 规模与来历 · 底层概念 |
| 2 核心模型 | 状态机、数据模型或事件契约，挑最能代表项目的一个 |
| 3–N 关键链路 | 一条链路一章 |
| 为什么这样设计 | W1…Wn，见 why-questions.md |
| 面试准备 | 角色 · 讲稿 · 挖坑 · 雷区 · 使用建议，见 interview-prep.md |
| 附录 | 代码索引 |

按项目调整：

- 链路少就合并成一章；项目有几种模式，就一种模式一章，再加一章对比。
- 有值得讲的工程点（同步、鉴权、密钥、终端、部署），加一章「其他工程点」。
- 项目很小（几百行），第 1 章和第 2 章可以合并，但 W 追问和面试准备不能少。

## 每一章怎么写

### 0 怎么读

- 第一句写「整份讲义只讲一件事：……」，冒号后面的核心句加粗。它以句号结尾，所以用 `<b>`，不用 `**`。
- 标签说明：【确定性】纯代码逻辑；【Agent】或【LLM】调模型的地方；【护栏】会拒绝、退回、暂停、要人介入的地方。项目里没有模型调用，就只留确定性和护栏，或者换成项目自己的分类。
- 「为什么」引用块和 W 编号的关系。
- 数字来自代码；「我的理解」是推断；「文档里有、代码里没找到」是没核到。
- 阅读顺序：底层不熟先看 1.6；第几章讲什么。

### 1 项目介绍

- **1.1 这是什么**：一句话定位（加粗），说清形态：服务、命令行工具、桌面应用、库还是 Agent，给谁用。再列 3–4 条组成要点。
- **1.2 要解决的问题**：3–5 条，编号。每条一个具体场景。不写「提高效率」这种话。
- **1.3 核心思路**：2–3 条原则。每条一句话，括号里写出处（ADR、注释、设计文档）。
- **1.4 系统全貌**：结构图；自上而下每层一两句；跟一个「为什么」引用块。
- **1.5 规模与来历**：表格，见下。
- **1.6 底层概念**：见下。用户说过「底层不是很懂，要讲细」，这一节不能省。

规模与来历表：

| 项 | 数 | 出处 / 说明 |
|---|---|---|
| 模块 | 数 + 名字 | 构建文件里的 workspace members / modules |
| 代码 | 按语言分的行数 | repo_facts.py；写明含不含空行、注释、测试 |
| 测试 | 用例数；跑没跑过；结果 | 报告文件（surefire、junit、.pytest_cache）、框架统计，或提交说明里记的结果（写明是这个来源） |
| 文档 | README、设计文档、ADR 份数 | 路径 |
| git 历史 | 提交数、作者、时间跨度 | git log；导入或重放的历史要写明 |
| 部署 | 有没有；在哪 | Dockerfile、CI、线上地址；没有就写没找到 |
| 来历 | fork、参考、改编 | NOTICE、LICENSE、README 里的声明 |

底层概念小节：

- 把项目里的每个「东西」落到机器上：它是进程、线程、协程、目录、文件、端口、容器、表，还是一条记录？谁创建？活多久？
- 用一张表：`名字 | 本质 | 在哪 | 活多久`。
- 讲清用了哪个框架、哪个 harness：web 框架、ORM、任务队列、Agent 框架，或者直接调官方 CLI。框架负责什么，项目自己负责什么。
- 讲清谁调谁、怎么通信：同进程的库调用、子进程、HTTP、stdio、消息队列、共享数据库。
- 同一个词有两种意思的，单独讲。比如「线程」可能指一条对话记录，不是操作系统线程。
- 有进程树或目录布局的，画一张图，或者用代码块画树形。

### 2 核心模型

顺序：生活例子 → 定义（三句话以内）→ 不用它会怎样 → 项目里的对应 → 真实代码 → 图 → 为什么这样建模。

生活例子参考：

| 概念 | 生活例子 |
|---|---|
| 状态机 | 网购订单：待支付 → 已支付 → 已发货 → 已完成；「已发货」时改地址会被拒绝 |
| 幂等 | 电梯按钮：按一次和按十次效果一样 |
| 版本号 / 乐观锁 | 共享文档：保存时发现别人改过，先刷新再改 |
| 租约 | 图书馆借书：到期不续，书自动回到架上 |
| 队列 | 餐厅点菜单：前台下单，后厨按顺序做 |
| 缓存 | 常用的书放桌上，不常用的放书架 |
| 事件日志 | 银行流水：余额是算出来的，流水只追加不修改 |
| 隔离 | 每个孩子一套文具，互不借用 |

贴代码的规矩：

- 只贴 10–30 行真实代码。删掉无关分支，用 `// …` 或 `# …` 标出删减。不改逻辑。
- 每行或每段末尾加中文注释，讲这一行在防什么。
- 代码块下一行写出处：`<sub>出处：path/to/file.py 的 apply()</sub>`。

### 3–N 关键链路

每章的结构：

1. 开头一句：这条链路从哪到哪，谁触发。
2. 时序图 + 图注。
3. 分步说明。编号和图里的圆圈编号对应。每步写：谁做、做什么、失败怎么办，后面标【确定性】【Agent】【护栏】。
4. 每个机制后面跟一个「为什么」引用块，标题括号写 W 编号。
5. 失败怎么收场：每种失败的去向（重试、退回、暂停、报错），做成表格。
6. 有真实踩坑的（提交说明、注释里记着），加一个「可以讲的一次排查」引用块。面试时很加分。

### 附录：代码索引

`| 文件 | 讲义里对应的内容 |`。按链路顺序排，只列讲义里提到的文件。

## 写法

- 短句。一段讲一件事。先结论，后理由。
- 不用套话：赋能、抓手、闭环、极致、全方位、深度融合、显著提升、助力。
- 数字写单位和口径：「约 1.2 万行（含测试和空行）」。
- 类名、函数名、表名、命令、路径用反引号。
- 中英文之间留一个空格。
- 没把握的话标出来：
  - 「我的理解」：推断，不是文档原话。
  - 「文档里有、代码里没找到」：README 或设计文档写了，代码里没有。
  - 「代码里有，但没有调用方」：写了没用上。
- 图注放在图下面：`<i>图 N · 标题。一句话说明怎么看。</i>`。

引用块（提示框）的种类：

| 标题 | 放什么 |
|---|---|
| 为什么……（Wn） | 设计理由的短版，2–4 句 |
| 面试这样说 | 一段能直接说出口的话 |
| 一句话答案 | 一个常被问到的问题的最短回答 |
| 这一节需要你改 / 注意 | 要用户确认、或者容易说错的地方 |
| 可以讲的一次排查 / 反转 | 真实踩过的坑、推翻过的方案 |
