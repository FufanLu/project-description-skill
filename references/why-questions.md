# 「为什么这样设计」怎么写

面试官最爱问：为什么这样？为什么不那样？这一章给每个关键设计准备一段能直接说出口的回答。

## 数量和编号

- 每个关键机制至少一问。一般 15–40 问。
- 按章节分组：A · 架构与边界、B · 核心模型、C · 链路一……分组标题的锚点 `wg-a`、`wg-b`。
- 编号 W1…Wn 全文唯一，锚点 `w1`、`w2`……
- 正文里的「为什么」引用块写短版（2–4 句），标题括号写编号：`> <b>为什么先查缓存（W2）</b>`。追问章写完整版。两处说法要一致。
- 追问章的标题写成「为什么这样设计：N 个追问」，N 是实际题数。

## 理由从哪来

按可信度排：

1. **代码注释**：离代码最近，最可信。
2. **ADR、设计文档**：一般写着背景、备选方案和取舍。
3. **提交说明、PR 描述**：fix、revert 的提交常常记着真实踩过的坑。
4. **测试用例**：测试名往往就是规则，比如 `test_rejects_stale_version`。
5. **我的理解**：以上都没有，才自己推断，并且标出来。

找法：

```bash
# 注释里的理由（按项目语言改 --include）
grep -rnE "because|why|instead|otherwise|so that|invariant|NOTE|HACK|SAFETY|因为|否则|为了|避免|注意" --include='*.py' <仓库>
# 修过什么、推翻过什么
git -C <仓库> log --format='%h %ad %s' --date=short | grep -iE "fix|revert|workaround|hotfix|修复|回滚|改为"
```

repo_facts.py 最后一节列了注释里理由线索最多的文件，先从那些读。ADR 重点看 Context、Decision、Consequences、Alternatives 这几段。

## 每一问的格式

```markdown
<a id="w3"></a>

#### W3 为什么 X 用 Y，而不是 Z？

先给结论。再讲不这样会出什么问题。最后讲代价。3–6 句，能直接说出口。

<sub>出处：path/to/file.py 的 foo() 注释 · docs/adr/0003.md</sub>
```

## 回答的结构

1. **结论**：一句话。
2. **反事实**：不这样会怎样。写具体的失败形态，不写「会有问题」。
3. **代价**：这个选择放弃了什么。
4. **真实踩坑**（有就写）：在哪个提交或注释里记着。

例子（虚构）：

> 坏：因为 Redis 性能好。
>
> 好：跳转是读多写少。先查 Redis，没命中再查库并回填，大部分跳转不碰数据库。代价是改了目标地址要删缓存；删失败就会读到旧地址，所以缓存设了 10 分钟过期兜底。

## 找问题的方向

- **选型**：为什么用 A 不用 B（语言、框架、存储、协议）。
- **边界**：为什么拆成这几个模块或进程；为什么这一层不能直接调那一层。
- **模型**：为什么这个状态单独一个字段；为什么做成纯函数。
- **并发与一致性**：为什么要锁、版本号、幂等键；锁的范围为什么是这么大。
- **失败**：为什么失败了退回而不是重试；为什么是这个顺序（先 A 后 B）。
- **数字**：为什么超时是 5 秒、最多重试 3 次。找不到理由就说「代码里是这个值，没找到选它的理由」。
- **反转**：为什么删掉了某个功能、推翻了原来的方案。这类题最加分。
- **代价**：这个设计最大的代价是什么。

## 红线

- 不把自己的推断写成「作者认为」「设计上是为了」。推断就标「我的理解」。
- 找不到理由的数字，就说没找到理由，不编一个。
- 不说「完全安全」「不会出错」这类绝对的话。
