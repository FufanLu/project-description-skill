# 面试准备：角色、讲稿、挖坑、雷区

这一部分参考了开源 skill interview-experience-breakdown（https://github.com/00menghui00/interview-experience-breakdown ，MIT 许可）的讲稿、6 组挖坑提问和雷区清单的写法，改成以代码为证据。它的红线同样适用：如实反映角色，不夸大，不编造。

顺序：角色 → 讲稿 → 挖坑提问 → 雷区清单 → 使用建议。

## 1 角色

先列仓库里能看到的事实，每条带出处：

- git 作者和提交分布（`git shortlog -sn`）；提交是不是集中在一两天（导入或重放）。
- 提交说明里的 Co-Authored-By，比如由编码 Agent 协作完成的提交。
- 文档、ADR 的署名；README 里的团队信息；LICENSE、NOTICE 里声明的上游。
- 有没有其他协作者、PR、代码评审的痕迹。

然后：

1. 事实不清，就用「这一节需要你改」引用块，列出要用户确认的问题：哪些是你写的？团队几个人？你负责哪块？花了多久？有没有上线、有没有真实用户？
2. 给一段「面试这样说」的建议说法，只按已知事实写，并注明要按确认后的情况改。
3. 不写「我一个人手写了 X 万行」，除非事实如此。代码大量由编码 Agent 写的，就讲清自己做了哪些决策、怎么验收。

## 2 讲稿（2–3 分钟）

要求：

- 第一人称，自然段，4–5 段，500–650 字。
- 讲判断和取舍，不堆名词。一句话里最多一两个技术名词。
- 挑 1–2 件最能体现判断的事细讲：遇到什么问题 → 第一反应 → 为什么不行 → 最后怎么做 → 代价。
- 数字只用有出处的。
- 复盘要真实：一个不足 + 下次怎么做。用户没说过的，留括号请用户自己填，不替用户编。

结构：

| 段 | 内容 | 时长 |
|---|---|---|
| 背景与角色 | 项目是什么、解决什么问题、我是什么角色 | 约 30 秒 |
| 亮点一 | 一个关键判断 | 约 45–60 秒 |
| 亮点二 | 另一个关键判断 | 约 45–60 秒 |
| 结果 | 规模、测试、真实使用（都要有出处） | 约 20 秒 |
| 复盘 | 一个不足、下次怎么做 | 约 20 秒 |

讲稿后面加一行斜体提醒：讲稿里描述「我做了什么」的句子，都要按角色一节确认过的事实改。

再跟一节「讲稿使用建议」：

```markdown
#### 讲稿使用建议

- **总时长**：约 2.5 分钟。
- **节奏切分**：
  - 背景与角色：约 30 秒。
  - 亮点一：约 50 秒。这是最亮的部分，可以放慢。
  - 亮点二：约 45 秒。
  - 结果与复盘：约 35 秒。
- **重音词**：「……」「……」
- **可能被追问的点**：
  - 「……」→ 讲 3.2、W5。
```

## 3 挖坑提问（6 组，共 15–21 题）

出题依据：简历原话（重点）、讲稿、代码里容易说错的地方。

| 组 | 考察什么 | 典型问题 |
|---|---|---|
| 第一组 · 澄清与背景 | 抓不抓得住核心；角色真实性 | 一分钟讲清解决什么；和现成方案有什么区别；这些是你写的吗；是 fork 吗 |
| 第二组 · 理解深度 | 核心模型和关键概念 | 为什么这样建模；某个概念的准确定义 |
| 第三组 · 方案与实现 | 一条链路讲到底；失败处理 | 从请求进来到返回讲一遍；任一步崩了会怎样 |
| 第四组 · 核心攻坚 | 讲稿里最亮的部分经不经得起追问 | 连环追问三层 |
| 第五组 · 结果与协作 | 数字怎么来；真实使用；怎么协作 | 测试测了什么；效果怎么量化；和谁协作、怎么分工 |
| 第六组 · 反问与假设 | scale 思维、自我认知 | 用户涨 10 倍、给团队用要改什么；最大的局限；重做会改什么 |

出题规则：

- 简历上每个漂亮的词都要有一题追问：主导、从 0 到 1、显著提升、高并发、X 万行、全部通过、自动、实时、零故障。
- 讲稿里越自信的地方，越要设计连环追问。
- 说法和代码不一致的地方一定出一题。比如简历写「实时推送」，代码是每隔几秒轮询。

每题的格式（每题一个锚点 `qN`，每组一个锚点 `qg-N`）：

```markdown
<a id="q5"></a>

#### Q5 问题原话（尽量用简历或讲稿里的说法）

> **面试官想考察**：……
>
> **回答注意**：先说什么；指向哪一章、哪个 W；哪里容易露馅；代码里能拿出什么证据。
```

## 4 雷区清单

一张三列的表：

```markdown
| 雷区（简历或讲稿原话） | 面试官的怀疑 | 代码里的证据与策略 |
|---|---|---|
| 「……」 | …… | 证据：……。策略：如实说 / 改措辞 / 删掉 |
```

雷区常见的来源：

- 数字：行数、测试数、性能数字、用户数。能不能说出是怎么测的。
- 绝对的词：全部、自动、实时、零、完全。
- 技术栈里只在边角用到的技术。
- 占位、没实现、默认不编译的模块。
- 参考或改编自上游的部分。
- 口头说法和代码不一致的地方。

每一行的策略三选一：如实说（给出处）；改措辞（给出改后的原话）；删掉。

## 5 使用建议

```markdown
#### 使用建议

- **自己走一遍**：先不看答案，把挖坑题和追问章大声答一遍，录下来听。
- **最容易露馅的题**：Qx、Qy……，重点准备；其中和简历措辞直接相关的，先改简历。
- **演练**：请人按第三组连续追问三层，每一层都能答到代码层面就过关。
```
